## 教材的核心主線

**事前準備：** 來源文件 → 解析與清理 → 切成小段 → 轉成向量 → 保存原文、向量及來源資訊。

**使用者提問：** 接收問題 → 視歷史處理追問 → 搜尋相關小段 → 補充或整合上下文 → 組合問題與提示 → 模型產生回答 → 呈現答案與可用來源 → 保存對話供下次使用。

切片與向量化的目的，是讓系統先選出有限的相關內容，再交給模型處理。資料建置與每次問答分開；提問本身仍可能需要向量化，不能說 embedding 只在資料匯入時使用。

## 兩套實作的差別

| 項目 | rag-chatbot | Qdrant contextual 教材 |
| --- | --- | --- |
| 入口 | React／Vite、FastAPI、WebSocket | Gradio 文件處理與聊天畫面 |
| 語言模型 | 本地 llama.cpp 的相容介面 | 現行預設為本地 Ollama；保留雲端選項 |
| 向量資料 | SentenceTransformer＋Chroma | 相容 embedding 介面＋本地 Qdrant |
| 文件處理 | 正式流程以 Markdown 為主；實驗另探索 PDF | PDF、TXT、DOCX、CSV、Excel 載入器 |
| 切片預設 | 字元長度 1000、重疊 50 | 字元長度 500、重疊 80 |
| 上下文整合 | Create-and-refine、tree-summarization | 3 個種子，補前後各 1 段，種子優先保留，最多 5 段 |
| 更新 | SQLite registry 追蹤新增、變更、刪除 | 畫面處理文件時會全量清除與重建 |
| 對話 | 全域短暫歷史；RAG 路徑可呼叫模型改寫追問 | 會話鏈改寫追問，近 2 輪記憶 |
| 回答方式 | 最終答案可逐字串流 | 回答完成後顯示，再附檢索來源預覽 |

具體程式參考：chatbot 的 `scripts/memory_builder.py`、`backend/services/chat_service/conversation_handler.py`、`ctx_strategy.py`、`backend/memory/vector_database/chroma.py`；Qdrant 版的 `document_loader.py`、`qdrant_vector_store.py`、`contextual_retriever.py`、`rag_system.py`、`app.py`。

**Create-and-refine 的設計：** 第一段建立初答，後續逐段加入資訊修正，最後形成答案。

**Tree-summarization 的設計：** 各段先形成局部答案，再分組整合，逐層合併到最終答案。

**這份 Qdrant 教材的 contextual retriever：** 指依文件及段落位置補入相鄰內容，再去重、限制數量；沒有獨立的內容重排序模型。

## 六層應如何理解

| 教材層級 | 白話意思 | 時間與責任 |
| --- | --- | --- |
| 1 數據源層 | 知識從哪裡來 | 文件、案件或外部資料來源 |
| 2 處理層 | 把資料整理成可查找的形式 | 清理、解析、切片、向量化 |
| 3 存儲層 | 保存內容及其來源 | 結構資料、向量、中繼資料與版本 |
| 4 檢索增強層 | 找到資料並整理成有用上下文 | 召回、篩選、排序、補上下文 |
| 5 生成層 | 根據上下文產生回答 | 問題、提示與模型輸出 |
| 6 應用與運維管控層 | 讓人使用、管理與評估服務 | 輸入輸出、權限、監控、評估、知識更新 |

六層是責任分類，並非使用者提問後必須依序走 1→6。使用者由應用層進入，檢索層查詢已建好的存儲，生成後再由應用層交回結果。六層架構中列出的完整企業能力，也不等於兩套示例或本作品全部完成。

## 教材說明與實作需要分開看

以下是讀碼發現，未修改教材，也未以實際執行驗證所有影響。

- **文件與預設設定不同：** Qdrant 原 README 仍主打 GPT-4o，現行設定已預設 Ollama。本地 GPU 及速度說明也混有歷史測試內容。
- **資料更新方式不同：** chatbot 有 registry 增量追蹤；Qdrant 畫面處理文件時全刪再建，不能直接當成增量索引範本。兩套都不能將現有隨機 chunk point ID 當成確定性內容 ID。
- **頁碼與來源需要檢查：** Qdrant loader 串接同一來源內容後，沿用第一頁 metadata；來源預覽不等同逐句引用或可靠頁碼定位。
- **上下文擴展仍有成本：** Qdrant 範例取相鄰段落時仍呼叫 `similarity_search(query="context")`，會額外計算 embedding。
- **介面開關不等於功能接好：** chatbot 的 Reasoning／Web Search 開關沒有在主要傳送路徑完成接線；MCP 搜尋、完整監控等主要出現在規劃筆記。
- **上下文精煉有實作落差：** chatbot `ctx_strategy.py` 使用 `enumerate(..., start=1)` 卻判斷 `idx == 0`，第一段不會走預期的建立初答分支。
- **模型設定必須一致：** chatbot CLI 建庫與 API 的預設 embedding 模型不同，直接依各自預設啟動存在不相容風險。
- **使用與失敗邊界：** chatbot 對話歷史全域共用，串流沒有明確完成事件；Qdrant 缺少資料時主要依提示拒答。兩者都不能僅靠畫面或提示文字宣稱完成多使用者隔離、可靠引用及答案品質驗證。

## 對目前採購專案的意義

- 本專案沿用先建資料、再檢索與生成的主線，另加入官方案件的精確 SQL 條件。
- 文件採種子與相鄰段落，但本專案目前上限是 **7 段**，不是教材 Qdrant 版的 5 段。
- 本專案使用確定性 point ID、內容／版本追蹤與獨立案件／文件 collections；這些要以自己的程式驗證，不從教材名稱推論。
- 價格統計、數字與引用驗證、生成失敗保留案件，是本專案額外的規則與防護。
- 本專案的追問主要為規則式背景沿用；尚未等同教材呼叫模型進行完整追問改寫。沒有實作的 reranker、網搜、權限與正式監控不應畫成已完成能力。
